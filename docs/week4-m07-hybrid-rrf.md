# W4-M07 chunk hybrid retrieval

## Design

Both retrievers operate on the same `arxiv-papers-chunks` documents. BM25 searches `paper_title^3`, `section_title^2`, and `chunk_text`; vector retrieval embeds the query with normalized `BAAI/bge-small-en-v1.5` vectors (384 dimensions, local CPU) and searches the Lucene HNSW cosine index. Category and publication-date filters are generated by the application and applied independently to both candidate paths.

For a chunk at one-based rank `r`, RRF contributes `1 / (k + r)`. The default `k` is 60. Raw BM25 and cosine scores are retained only as source-specific diagnostics: their scales and meanings differ, so weighted raw-score addition would not be sound. Each retriever supplies `min(100, final_size * 4)` candidates. Results are deduplicated by `chunk_id`; BM25 metadata deterministically wins a conflict. Ties use best individual rank and then `chunk_id`.

If one retriever fails, the response remains successful as `bm25_fallback` or `vector_fallback` and includes a degradation reason. Both failures raise a hybrid error and map to HTTP 503. Empty successful rankings are not failures.

`POST /api/v1/hybrid-search` accepts query, size, categories, and date bounds. The lifespan creates one lazy embedding provider per Uvicorn worker. Repeated requests in one worker reuse it; separate workers cannot share Python model state.

## Chunking and index context

The Week 4 chunker targets 600 words, prefers a minimum of 100 words, and uses 100-word overlap. It prefers persisted structured sections, combines adjacent small sections where sensible, keeps coherent sections intact, splits oversized content near the target, and falls back to overlapping `raw_text` chunks. The live corpus is 15/15 raw-text fallback because Docling sections are not persisted. The resulting index contains 513 normalized embedded chunks from 15 papers.

## Live ranking observations

The six required queries were compared at BM25, vector, and hybrid top five. Full identifiers, ranks, scores, and previews are in the M07 acceptance report. Summary:

| Query | BM25 top chunk | Vector top chunk | Hybrid top chunk | Assessment |
|---|---|---|---|---|
| underserved patients | 2609.19793/028 | 2609.19793/028 | 2609.19793/028 | both reinforce the same wearable-health chunk |
| clinical bias/fairness | 2610.01963/000 | 2610.01963/002 | 2610.01963/000 | hybrid concentrates on the correct clinical-bias paper |
| robots/world representations | 2610.10528/000 | 2610.10515/008 | 2610.10528/000 | vector top passage is more semantically specific; hybrid is not clearly better |
| low-income student adoption | 2609.36129/000 | 2609.36129/001 | 2609.36129/000 | both strongly identify the FGLI paper |
| smart buildings | 2610.01647/000 | 2610.01647/001 | 2610.01647/000 | both strongly identify the cloud/fog/edge paper |
| disadvantaged patients | 2610.01963/002 | 2610.01963/002 | 2610.01963/002 | exact and semantic evidence reinforce the equity/undertriage chunk |

BM25 title boosting helps exact overlap identify the correct paper, but every chunk repeats paper metadata, producing identical BM25 scores for some papers. Vector search can select a more passage-specific chunk. Chunks present in both rankings receive the strongest RRF reinforcement. The robotics example shows that fusion is not automatically superior: BM25's repeated-title evidence can dominate a semantically better vector passage.

### Actual RRF calculation

For query `AI systems helping underserved patients get medical care`, chunk `2610.01963::chunk::002` was BM25 rank 2 and vector rank 9 within the 20-candidate pools:

```text
1 / (60 + 2) + 1 / (60 + 9)
= 1/62 + 1/69
= 0.030621785881252923
```

This was the implementation's third-ranked hybrid result.

## Filters, performance, and runtime

A live `cs.RO` filter returned only chunks containing `cs.RO`, with ranks from both retrievers. A `2026-09-28` date range returned only chunks published that day. No out-of-filter chunk entered either fused result set.

Across six warm queries at candidate depth 20:

| Stage | Average ms | Min-max ms |
|---|---:|---:|
| BM25 | 36.91 | 24.75-74.77 |
| query embedding | 296.29 | 43.09-621.35 |
| vector search | 28.87 | 25.08-40.35 |
| RRF and normalization | 0.85 | 0.73-1.19 |
| total | 362.92 | 97.20-702.94 |

Cold BGE initialization was 39.48 seconds in this run. One single-worker API process reached about 992 MiB RSS after loading BGE. Its first request took 19.78 seconds and its next request 259 ms; logs showed one model load. The current Docker command uses four workers, which could approach roughly 4 GiB of worker RSS once every worker loads BGE, in addition to OpenSearch and other services. Production deployment should measure concurrency needs and likely begin with one embedding-enabled worker or a separately managed embedding service. The worker count was not changed in this milestone.
